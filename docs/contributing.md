# Contributing

Read [repository-layout.md](./repository-layout.md) first — it answers "where
does my code go?", which is the question most changes hinge on.

Before pushing:

```bash
npm run check   # paths + boundaries + typecheck + tests
```

## Adding a reusable package

1. Create `packages/<name>/` with a `package.json` named `@av/<name>`.
2. Add the path to `workspaces` in the root `package.json`.
3. Register it in `compose.config.json` under `components`, declaring its
   `capabilities` and `requires`, and set `"standalone": true`.
4. Add it to whichever `profiles` should include it.
5. Run `node tools/gen-docs.mjs` to generate its reference page.
6. `bun install`.

Do not import anything from `studio/` — that is what makes it a package rather
than a module. `check:boundaries` will tell you immediately.

## Adding a capability

Capabilities are provider-neutral (ADR-0015). A stage asks for
`speech.synthesize`; it never asks for a particular vendor.

Use this end-to-end checklist (Blender is the scene-provider example):

1. Define the provider-neutral input/output semantics. Reuse a capability only
   when its semantics match; source creation, rendering and editing are different.
2. Add new names to both `studio/contracts/src/vocabulary.mjs` and
   `schemas/v1alpha1/vocabulary.schema.json`; run `npm run bindings:generate
   --workspace @studio/contracts`. Extend `fixtures/vocabulary/valid/bindings.json`
   and add schema fixtures/conformance tests. `npm run check:contracts` verifies
   vocabulary, fixtures and generated bindings (also run by root `check`).
3. Implement a reusable `@av/*` package with validation, readiness probing,
   explicit provider/device selection, bounded cancellable execution, provenance,
   and failed-output handling. Packages never import studio concepts.
4. Register the workspace, component requirements and selected profiles in
   `compose.config.json`. Multiple providers are supported: each overlapping
   capability needs an explicit profile `defaultProviders` choice. No silent fallback.
5. Add the agent dependency and a small studio adapter/tool-registration module.
   Register it in `studio/agent/extensions/index.ts`. Check composition bindings
   and live readiness; respect episode paths including symlinks. Throw tool errors
   rather than returning an `isError` property from Pi tool `execute`.
6. Add the technique/stage skill to `skills/`, and a versioned manifest or a
   documented integration into an existing workflow. Describe native-source
   handoffs, preview/final settings, and how an accepted result reaches the edit.
   Do **not** add production handlers to the gateway.
   A stage the execution service should perform on its own — rather than Pi
   performing it through a tool — gets a descriptor in `studio/adapters`
   (see its README); its conformance test checks the match against the
   built-in pipelines.
7. Test fake success/failure, missing outputs/binaries, cancellation, contention,
   trust/path boundaries and source preservation; add an opt-in live smoke test.
   Test actual skill/tool discovery and pipeline validation as well as the package.
8. Run `bun install`, compose the intended profile, run doctor, regenerate docs,
   then `npm run check`. Validate profiles without the new provider too. Record
   external requirements and unverified live behavior; do not equate “wired” with
   “ready” or “authorized.”

This is still too many manual integration points. `studio/adapters` is the
thin first step of the adapter registry the [harness review](https://github.com/phoebus-84/video-studio/blob/bfea2f80a4f8a10c999118a4db35b2820ac5c5fc/docs/harness-review.md)
proposes: it pairs stages with the code that performs them by declaration, but
readiness, estimates, jobs and per-episode bindings are not in it yet, and it is
not a plugin API.

## Adding a skill

- Reusable technique → `skills/shared/`
- Production stage → `skills/studio/`

`skills/` is the source of truth; `.pi/skills/` is generated by `compose`
(ADR-0029). Never edit `.pi/skills/` — the next compose overwrites it.

## Adding or changing a pipeline

Pipeline manifests live in `studio/pipelines/pipelines/`. They validate against
the canonical schema owned by `studio/contracts` (ADR-0024) — this package does
not define its own.

```bash
npm run check:pipelines
```

## Dependencies

Use `workspace:*` for anything inside this repository. **Never `file:../`** — it
installs as a symlink holding an absolute path, which is how the predecessor
layout became uninstallable on every machine but one. `check:paths` fails the
build if an absolute path reappears.

Reach for a package by name, never by relative path. `../../other/src/thing.ts`
is a boundary violation even when it happens to resolve.

## Documentation

The site is [VitePress](https://vitepress.dev):

```bash
npm run docs:dev       # local server with hot reload
npm run docs:build     # production build; fails on any dead internal link
npm run docs:preview   # serve the built site
```

What is hand-written and what is generated:

| Path | |
|---|---|
| `docs/*.md`, `docs/adr/` | hand-written |
| `docs/packages/`, `docs/studio/` | **generated** by `tools/gen-docs.mjs` from `compose.config.json` |
| `docs/reference/` | **generated** by `tools/sync-doc-sources.mjs`, gitignored |

Component reference pages take their facts — capabilities, requirements, tier,
package name — from `compose.config.json`, so a page cannot disagree with what
the composer will actually do. `npm run docs:check` fails if they are stale;
run `npm run docs:generate` after changing the manifest.

Each component's own Markdown stays next to its code. It is copied into
`docs/reference/` when the site builds, with relative links rewritten to
resolve in the site. **Edit it where it lives** — the copies are overwritten.

The sidebar is derived: components come from the manifest and ADRs are read
from disk, so neither needs registering by hand.

A decision that constrains future work gets an ADR in `docs/adr/`. Number it
sequentially and say what it supersedes, if anything.
